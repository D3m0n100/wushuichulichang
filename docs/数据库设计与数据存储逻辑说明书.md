# 污水厂监测数据库设计与数据存储逻辑说明书

版本：2026-07-13 Storage V2.1  
数据库：`sewage_monitor`  
数据库版本：MySQL 8.0 / 8.4  
数值精度：所有业务测量值统一保留小数点后三位。

监测信号统计口径：`monitor_point` 保存 37 条基础监测点配置，其中包括一期、二期瞬时流量；新增的一期、二期累计流量使用独立表保存，不重复登记到 `monitor_point`。因此数据库基础点位配置为 37 条，后端实际读取的测量信号共 39 个。

## 一、核心存储逻辑

1. B1 PLC 的一期累计流量点位 `B1_PHASE1_FLOWMETER_TOTALIZER`（DB2.DBD108）每分钟读取一次，写入 `monitor_phase1_totalizer`。
2. B1 PLC 的二期累计流量点位 `B1_PHASE2_FLOWMETER_TOTALIZER`（DB2.DBD112）每分钟读取一次，写入 `monitor_phase2_totalizer`。
3. 同一分钟的一期累计量与二期累计量相加，结果写入 `monitor_totalizer_snapshot`。
4. 一期、二期瞬时流量分别映射为 `Z-FIT01`、`Z-FIT02`，每分钟各写一行到 `monitor_point_data`。
5. 每小时从 `monitor_point_data` 计算上一小时的平均值，`monitor_metric_hourly` 每小时写入两行。
6. 每天零点从 `monitor_point_data` 计算上一天的平均值，`monitor_metric_daily` 每天写入两行。
7. 其余 35 个监测点的小时值写入 `monitor_point_hourly`，日值根据小时表计算后写入 `monitor_point_daily`。
8. 设备故障当前状态写入 `monitor_device_fault_state`；首次活动报警、报警状态变化和恢复事件写入 `monitor_device_fault_event`。

## 二、完整表清单

| 序号 | 表名 | 用途 | 主要写入周期 |
|---:|---|---|---|
| 1 | `monitor_point` | 37 个监测点的基础配置 | 初始化或配置变更 |
| 2 | `monitor_point_data` | 一、二期瞬时流量分钟数据 | 每分钟两行 |
| 3 | `monitor_phase1_totalizer` | 一期流量计累计流量 | 每分钟一行 |
| 4 | `monitor_phase2_totalizer` | 二期流量计累计流量 | 每分钟一行 |
| 5 | `monitor_totalizer_snapshot` | 一、二期累计流量合计 | 每分钟一行 |
| 6 | `monitor_metric_hourly` | 一、二期小时平均流量 | 每小时两行 |
| 7 | `monitor_metric_daily` | 一、二期日平均流量 | 每天两行 |
| 8 | `monitor_point_hourly` | 其余 35 个监测点的小时值 | 每小时每点一行 |
| 9 | `monitor_point_daily` | 其余 35 个监测点的日统计值 | 每天每点一行 |
| 10 | `monitor_device_fault_state` | 设备最新故障状态 | PLC 轮询时更新 |
| 11 | `monitor_device_fault_event` | 故障发生与恢复事件 | 状态变化时新增 |
| 12 | `monitor_schema_migration` | 已执行的数据库迁移版本 | 数据库升级时 |

### 辅助查询视图

数据库另外提供 3 个只读视图，视图不单独保存数据：

| 视图名 | 字段 | 用途 |
|---|---|---|
| `vw_inflow_totalizer_latest` | `totalizer_sum_value`、`latest_collect_time` | 查询最新一期与二期累计流量合计 |
| `vw_inflow_hourly_total` | `stat_hour`、`total_hour_avg_value`、`sample_count` | 按小时查询两期平均流量合计 |
| `vw_inflow_daily_total` | `stat_date`、`total_day_avg_value`、`sample_count` | 按日期查询两期平均流量合计 |

## 四、设备故障覆盖检查结论

- 后端轮询全部 PLC 模块的 `overview.devices`。
- 设备只要在 PLC 点位定义中配置了故障报警地址，读取结果就会包含 `fault` 字段。
- 每次读到 `fault` 后，都会更新 `monitor_device_fault_state`。
- 首次读到活动故障或故障状态发生变化时，会在 `monitor_device_fault_event` 新增 ACTIVE/RECOVERED 事件。
- 没有配置故障报警地址的设备不会虚构故障数据。
- 单个 PLC 或单个设备读取失败时不会写入假状态，保留最后一次有效状态。

## 六、验证规则

可使用以下规则快速检查运行结果：

- `monitor_point_data`：正常运行一小时后，Z-FIT01 和 Z-FIT02 应各约 60 行。
- `monitor_phase1_totalizer`、`monitor_phase2_totalizer`：正常运行一小时后应各约 60 行。
- `monitor_totalizer_snapshot`：两期累计量均有效时，一小时约 60 行。
- `monitor_metric_hourly`：每个完整小时应新增两行。
- `monitor_metric_daily`：每天零点后应为上一天新增两行。
- 所有数值字段查询结果应最多显示三位小数。


## 七、进水流量历史只读接口

接口：`GET /api/monitor/metrics/inflow/history`

查询参数：

| 参数 | 格式 | 含义 |
|---|---|---|
| `start` | `yyyy-MM-dd HH:mm:ss` | 查询开始时间，包含该时刻 |
| `end` | `yyyy-MM-dd HH:mm:ss` | 查询结束时间，包含该时刻 |
| `intervalMinutes` | 1-1440 的整数 | 聚合间隔，前端当前提供 5、10、15、30、60 分钟 |

返回的 `rows` 数组包含以下字段：

| 字段 | 数据来源 | 单位 |
|---|---|---|
| `collect_time` | 聚合时间点 | - |
| `phase1_instant` | `monitor_point_data` 中 `Z-FIT01` 的区间平均值 | m³/h |
| `phase2_instant` | `monitor_point_data` 中 `Z-FIT02` 的区间平均值 | m³/h |
| `instant_sum` | 同一时间区间一期、二期瞬时平均值之和 | m³/h |
| `phase1_totalizer` | `monitor_phase1_totalizer` 区间内最后一条读数 | m³ |
| `phase2_totalizer` | `monitor_phase2_totalizer` 区间内最后一条读数 | m³ |
| `totalizer_sum` | `monitor_totalizer_snapshot` 区间内最后一条合计快照 | m³ |

该接口只执行参数化 `SELECT` 查询，不修改数据库、不调用 PLC。单次查询最多返回 10000 个聚合时间点，超过时应提高查询间隔或缩短时间范围。
